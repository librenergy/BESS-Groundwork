# Log

## 2026-09-02 (segment `PoC` → `POM`; ported from the first project clone)

* **`PoC` (Point of Connection) renamed `POM` (Point of Metering)** across segment-types, taxonomy (block type, instance grammar `POM-{N}`, external-segment list, substation contents, graphs) and the canonical head-end model. First-clone lesson: the old name conflated the commercial metering boundary — the revenue meter, where every measured guarantee actually lives — with the physical point of interconnection, which typically carries no metrics. Projects that need the physical POI name it as its own boundary.

Maintained through the `ontology` session; the `definitions-taxonomy` skill keeps the glossary side.

## 2026-08-31 (SOC terms split by basis)

* **The two SOC terms replaced by four basis-explicit ones**, ported from the first project's ratification: `soc_percent_installed` / `soc_percent_contract` / `soc_kwh_installed` / `soc_kwh_contract`, with a stated rule that no bare `soc` term exists — installed and contract are different scales by design (bottom buffers/offsets, contract caps), and the installed→contract remap belongs to the State of Energy Mapping data product, not the vocabulary. This is the SoC-basis ambiguity the vocabulary's own "is not" discipline existed to catch, now resolved structurally instead of per-note.
* **Two refinements ported the same day:** the section now states that **"state of charge" here is really state of energy** (an energy quantity in Wh and capacity fractions, not electrochemical charge / coulomb counting; the SOC name is industry convention, SOE the same quantity), and `soc_percent_contract` is **never above 100% by construction** — the contracted range is defined so it cannot exceed it, so a value above 100% is a remap or denominator error; each project ratifies what its reported scale anchors 100% to (contracted vs installed) before trusting a counterparty feed.

## 2026-08-31 (metric classes)

* **Metric classes ratified in the layer-4 description, and a `class` column added to the registry projection.** Three classes, each deciding the metric's one definition home: `performance_guarantee` (contract-defined calculation; home is the PGM calc sheet; metric ID carries the governing contract as a suffix, since the contract is part of the identity), `engineering` (owner's physical view; home is the Metrics Tree sheet), `monitoring` (the long tail; compact tree rows). Rule stated once: **one definition home per metric, every other appearance is a link** — the tree references PG metrics without restating their calculations. The registry's `inputs` note now admits data-product inputs (an availability metric whose authoritative input is the outage event log, not telemetry, records exactly that).

## 2026-08-31 (the fill loop)

* **"Fill loop" section added to the main document, mirrored in the skill.** States the population discipline learned from the first project use: the ontology fills on demand, pulled by KPI-building work, never as a big-bang session. The only up-front step is the taxonomy prune; after that, each KPI runs classify (Metrics Tree, one metric per contract) → write the formula in measurement terms (ratify missing terms at that moment) → check the canonical model carries each input at the grain the telemetry actually reports → build against canonical columns. Division of labor stated once: ontology = nouns, Metrics Tree = verbs, DIR = where nouns come from; a word measured differently by two parties is two terms, one metric per contract, and a shadow metric, none sharing an identifier.

## 2026-08-31 (storage layers and alignment rules)

* **Canonical models gained the two-layer storage principle and the alignment rules.** New "Storage layers" section states the split: the narrow historian (one row per reading) is the system of record, the wide canonical table is the ratified subset pivoted and regularized to the ratified grain, and promotion between them is additive and reversible. New "Building the wide table" section fixes the five alignment rules: bucket to the grain, one bucket statistic per column, states may carry forward (with a staleness cap) but analogs are never interpolated in storage, late data is handled by idempotent upserts over a lookback window, and absent segment-intervals are absent rather than all-null rows. Rationale researched against Palantir Foundry's architecture: Foundry stores series narrow (syncs require unpivot), keeps alignment/interpolation lazy at query time, and can do so because it owns the query engine; a SQL-consumed platform materializes the wide layer instead.
* **Standards posture stated in one sentence** in the main document: informed by SOSA/SSN, SKOS, UCUM/QUDT, and IEC 61850 / MESA-SunSpec, adopted as design influences rather than referenced dependencies, per the maintainer's direction to keep attribution light.
* **Platform projection decision table extended** with the four decisions the build needs: historian layer location, canonical build mechanism, build cadence + lookback, and the state staleness cap.

## 2026-08-31

* **Resource created: Groundwork Ontology (ONT), v0.1.** Five documents: the main document (four layers, the class/binding/instance split that keeps the template platform-agnostic, the parameter/measurement/metric rule, identity and relation rules), the segment taxonomy (seeded with a generic ~38-type BESS taxonomy organized by chain, with containment parents and synonyms), the measurement vocabulary (curated core term set with the one-unit-per-term, statistics-are-not-terms, and grains-are-not-terms rules, born from real registry pollution patterns), the canonical data models (Battery String populated as the worked example, reverse-engineered from a live deployment's string table shape with no project content; PCS, Bat, Meter, BESS, TX, Weather Station as stubs), and the platform projection (four-table relational shape, six agent build directives ending in validation and an `ONT_VERSION` stamp).

* **Design decisions recorded at creation:** the metric layer stays in the Metrics Tree (ONT registers `kpi_code` identifiers only, preventing a second home for formulas); the ontology carries no `EIM_VERSION` because it sits at asset-class level, and instead *issues* an `ONT_VERSION` stamp that consuming documents carry; the "is not" column in the vocabulary is treated as load-bearing, since capability-vs-delivered and percent-vs-energy confusions are the recurring failure the vocabulary exists to prevent.
